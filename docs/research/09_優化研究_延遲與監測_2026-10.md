# 09　優化研究：延遲、監測、前端（2026-10-02）

> 範圍：負責人要求「system design 上的優化：latency 和監測，前端也要」。
> 方法：四條平行研究（後端延遲、系統監測、前端工程、前端介面），只讀程式碼不執行；每項發現都附檔案與行號。
> 標 **✓** 的項目由主要研究者另外讀原始碼核對過；其餘依研究者讀到的行號，修之前仍要再讀一次（教訓見 FAILURE_LOG P-1）。
> 時間標「估」的是推算，不是量測——目前的程式**量不出**各階段耗時（見 OBS-3）。

---

## 0. 一頁摘要

**延遲**
- 實測的 25–28 秒是 **Dify 模式**（LLM 只跑兩輪：解析 → 草擬）。交付預設是 `LLM_MODE=local`，會多跑兩輪：驗證器（BE-1 ✓）和請求項要件拆解，估 30–45 秒。
- 編排是「整層做完才進下一層」的關卡式（BE-2）。截止日、請求項樹這些不依賴草稿的步驟也在等草稿。
- 逾時是反的（BE-4 ✓）：閘道 60 秒放棄，AI 引擎對 Ollama 等到 600 秒。使用者重試時，前一個被放棄的呼叫還佔著 GPU。
- 做完第一、二波估可回到 18–22 秒；再加串流進度，第一段可用內容約 10 秒就出現。

**監測**
- 延遲直方圖最大桶只有 10 秒（OBS-1 ✓）。分析全部落在 +Inf，p95 圖永遠顯示 10，「p95 ≤ 25 秒」的 SLA 在 Prometheus 上算不出來。
- 引用移除率、prompt injection、成本、LLM 錯誤這些指標只有宣告、沒有寫入（OBS-2 ✓）。品質儀表板結構上永遠是綠的。
- 使用者看到的請求編號和日誌裡的關聯 ID 是兩個不同的 uuid（OBS-4 ✓）：「這筆分析很慢」查不到任何紀錄。
- 沒有任何告警規則（OBS-7）、沒有分階段耗時（OBS-3）、隱私防線觸發沒有計數（OBS-5）。

**前端正確性（會出錯的）**
- 分析中切換案件，A 案結果會顯示在 B 案下，還能簽核匯出（FE-1 ✓）。
- 任何 422 回應都會讓整個 app 當掉；重新整理就會登出（FE-2 ✓）。
- 查用量時把案號放進網址（FE-3／UX-18 ✓），違反「案號不進網址」的硬規則；稽核 API 寫死帶 `CASE-2025-001`（FE-4 ✓）。
- 引用牆顯示綠色「全部通過」，同時旁邊說有引用與段落不符（UX-2）。

**隱私（附帶發現）**
- 回應快取存的是**還原遮罩後**的明文，放在無密碼、無 TLS 的 Redis（BE-17 ✓）。`erase_subject` 刪不到。
- 日誌裡有使用者、IP、案號，以及租戶字典的原文樣式（OBS-8）。

## 1. 延遲

### 1.1 延遲預算（交付預設 `LLM_MODE=local`，2 條核駁，模擬嵌入）

| 階段 | 順序 | 依序的網路／LLM 呼叫 | 成本 |
|---|---|---|---|
| 認證、頻率、配額、ACL | 依序 | 0–4 次 Redis | < 5 ms |
| 遮罩 ×2 + 提示 | 依序 | 每個新實體一次 SQLite commit | 10–300 ms（估） |
| 解析 OA | 依序 | 1 次 LLM | 約 9 s（RunningPanel 校準值） |
| 檢索 ×N | 平行 | 1 次嵌入 + 2 次 Qdrant（＋重排） | 模擬 < 0.2 s；CPU 上跑 4B 重排可達數十秒 |
| 草擬 ×N | HTTP 上平行，但 Ollama 可能逐一處理 | 每條 1 次 LLM | 平行約 10 s；被序列化則 N×10 s |
| 驗證 ×N | 平行 | **local：每條 1 次 qwen**；dify：0 | 3–8 s（估） |
| 截止日 → 請求項樹 | 依序 | 2 次 HTTP | < 150 ms |
| 要件對照 ×N | 平行 | **local：每個獨立項 1 次 LLM** | 3–8 s（估） |
| 還原、用量、摘要、快取、稽核 | 依序 | 2–3 次 SQLite + Redis | 10–100 ms |

## 2. 監測

### 2.1 現況（已有的）
- 自寫的 Prometheus registry，標籤已避開 user_id／case_id（`metrics.py:360-466`）。
- 結構化 JSON 日誌、`X-Request-ID` 中介層，閘道 → AI 引擎有傳遞（`orchestrator.py:167`）。
- Sentry 預設關閉；開啟時前後端都有清洗（不送 body、frame locals、breadcrumb）。
- compose 有 Prometheus 3.6 + Grafana 12.2 與三張儀表板，抓取有 token。
- 稽核列（每請求一列，含延遲、模型、token、遮罩規則、閘道判斷）是最完整的離線遙測。

### 2.3 建議的最小黃金指標與 SLO

**允許的標籤**：service、路由樣板、method、status_class、cache、stage、backend、locality、security_level、intent、outcome、dependency、op、guard、result、decision；租戶 ID 只用在量與成本指標，且必須是不透明 ID。
**禁止的標籤**：case_id、user_id、request_id、專利號、IP、遮罩規則樣式。

**指標（10 個）**
1. `http_server_request_duration_seconds{service,route,method,status_class,cache}`
2. `analyze_stage_duration_seconds{stage,backend,outcome}`
3. `analyze_results_total{outcome}`
4. `llm_request_duration_seconds{backend,locality,intent,outcome}`、`llm_tokens_total{backend,model,kind}`

- **延遲（地端層）**：28 天內，快取未命中的分析 95% ≤ 30 s、99% ≤ 90 s。

## 6. 面試可以講的取捨

| 主題 | 一句話 | 對應 |
|---|---|---|
| 安全控制要跨部署模式一致 | 同一顆模型的第二意見沒有獨立性，只有延遲 | BE-1 |
| 關鍵路徑排程 | 用 DAG 取代整層關卡；並行度受最窄的一段限制（GPU） | BE-2、BE-3 |
| 逾時階層與截止時間傳遞 | 外層比內層短 → 放棄的工作還佔著資源，重試排在它後面 | BE-4 |
| async 裡的同步 I/O | 比純同步 handler 更糟：一個鎖等待卡住所有請求 | BE-6 |
| 體感 vs 實際延遲 | 串流的粒度由安全牆決定：驗證通過後才能送出 | BE-8 |
| 負向快取 | 失敗結果被快取會把短暫故障延長成一小時 | BE-10 |
| 桶界就是 SLO 的一部分 | 門檻不是桶的邊界就無法告警 | OBS-1 |
| 宣告但沒寫入的指標 | 是附帶圖表的偽陰性 | OBS-2 |
| 單一關聯 ID | 客戶看到的編號必須就是維運 grep 得到的 | OBS-4 |
| 隱私的 SLI 是必須維持為 0 的計數器 | 第一次增加就叫人，不吃錯誤預算 | OBS-5 |
| liveness vs readiness | 會打資料庫的 liveness probe 會造成重啟風暴 | OBS-9 |
| 遙測供應商也是資料處理者 | 和任何出口一樣做威脅模型 | OBS-13 |
| 資料以最不敏感的形式保存 | 快取存遮罩狀態，命中時再還原 | BE-17 |

  - bge-m3／重排器在這台機器上的 CPU 成本；SQLite fsync 成本。
