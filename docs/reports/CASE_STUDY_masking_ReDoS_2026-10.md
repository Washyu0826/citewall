# 個案報告：個資遮罩層的 ReDoS 與超線性運算（2026-10-07）

> 對應紀錄：FAILURE_LOG **B-52**（公開 demo 的可用性）、**B-53**（本案）、**P-20**（我在過程中的失誤）；
> SECURITY_AUDIT **H-12**。修正 commit：`3ebdeb4`（分支 `feat/phase5-deploy`）。

## 1. 摘要

送給任何模型之前，系統一定要先把個資換成佔位符（設計不變量 #3）。負責這件事的 `masking.redact`
有一條台灣地址的正規表示式，遇到一長串空白時會發生**災難性回溯**：3,000 個空白就要約 50 秒，
接近輸入上限時實際上永遠跑不完。另外有三個地方是 O(n²)：email 規則、實體重疊檢查、字串重組。

分析 OA 與遮罩預覽都會走這段程式，所以**任何登入的使用者**都能用一個請求佔住 gateway，
讓其他人的健康檢查、登入、分析全部卡住。在要完全公開的 demo 裡，「任何登入的使用者」等於「任何訪客」。
這個問題至少從 2026-09-26 的第一個公開版本就存在（地址規則在那時已經在裡面），不是部署時改出來的。

修正後，上限附近最刁鑽的輸入都在 0.35 秒內完成。用舊版與新版各跑 3 萬筆隨機文字，
遮罩結果**完全相同**，沒有任何輸入因此遮得比以前少。

## 2. 背景：遮罩在系統中的位置

```
瀏覽器 → nginx → gateway ─┬─ /v1/oa/analyze ──→ masking.redact → ai_engine → 模型
                          └─ /v1/debug/redaction_preview → masking.redact（SPA 送出前的預覽）
```

- `masking.redact` 依序做：Unicode 正規化（去零寬字元、易混淆字元折疊、NFKC）→ 內建個資規則
  （email、電話、身分證號、統編…）→ 租戶字典 → 實體偵測（人名、機構、地址）。
- gateway 是單一行程。正規表示式在 Python 裡執行時會持有 GIL，所以一個卡住的請求會拖慢同一行程的所有請求。

## 3. 怎麼發現的（時間線）

| 時間 | 事件 |
|---|---|
| 第 5 階段審查 | 獨立審查量到遮罩預覽「長度加倍、時間約 ×4」，而且沒有次數與大小限制（B-52 P5-M2）。 |
| 第一次修正 af9e67e | 我加上次數限制與「和分析相同的大小上限」（約 96K 字元），就在紀錄裡寫「已處理」。 |
| 再審查 | 指出上限**以內**仍是超線性：96K 的 `a` 要 9.2 秒，`Applicant: Ab, Ab, …` 要 33.5 秒。 |
| 我逐條量測 | 對每一條規則、每一種刁鑽輸入分別計時，找到更嚴重的地址規則：**3,000 個空白 49.5 秒**。 |

第一次修正的錯誤在於：只加上限，卻沒有在上限附近重新量最壞情況（P-20 第 1 點）。

## 4. 根因

### 4.1 地址規則的災難性回溯（最嚴重）

原本的規則（節錄）：

```
(?:[CJK]{1,4}[縣市])?\s*(?:[CJK]{1,4}[區鄉鎮市])?\s*[CJK0-9]{1,8}?(?:路|街|大道)\s*
(?:…段)?\s*(?:…巷)?\s*(?:…弄)?\s*[0-9]+…\s*號…
```

幾個**選用群組**中間夾著相鄰的 `\s*`。面對一長串空白、後面又湊不出「路／街＋號」時，
正規表示式引擎會嘗試把這串空白分給各個 `\s*` 的**每一種**切法；每個起點都要試一輪，
起點又有 n 個。實測：

| 輸入 | 時間 |
|---|---|
| 3,000 個空白 | 49.5 秒 |
| 接近上限（96K）| 實際上跑不完 |

### 4.2 email 規則的 O(n²)

`[a-zA-Z0-9._%+-]+@…` 的本地部分沒有上限。在一長串本地部分可用的字元（字母、數字、`.`、`-`）裡，
引擎從每一個起點都往後掃到底找 `@`，找不到才換下一個起點：n 個起點 × 平均 n/2 → O(n²)。
96K 個 `a` 約 9.7 秒。

### 4.3 實體偵測的 O(n²)

- `ner_spans` 依優先順序挑選不重疊的實體，每個候選都用 `any(...)` **掃過所有已選的實體與佔位符**。
  候選數與已選數都和文字長度成正比，所以是 O(n²)。
- `redact` 每遇到一個實體，就用 `redacted[:start] + placeholder + redacted[end:]` 重建整個字串，
  實體數 × 字串長度，也是 O(n²)。
- 96K 的 `Applicant: Ab, Ab, …` 約 33.5 秒（審查量測）。

### 4.4 大小上限量錯了對象

上限用原始長度估 token（字元 ÷ 3），但遮罩處理的是 **NFKC 正規化後**的文字。
有些字元會被展開：`㍻` → `平成`（2 倍），`ﷺ`（U+FDFA）→ 18 個字元。
所以 96K 字元可以在遮罩時變成 1.7M。

## 5. 修正，以及為什麼結果不變

遮罩是隱私的最後一道牆，修正的首要條件是**任何輸入都不能因此遮得比以前少**。

### 5.1 地址規則：佔有式量詞

把 `\s*` 全部換成佔有式的 `\s*+`。佔有式量詞吃下的空白不會再吐回去，
所以不會再去嘗試各種切法。

**為什麼結果相同**：在這條規則裡，每個 `\s*` 後面接的元素（中文字、數字、`路`、`號`…）都不可能比對到空白。
所以「把空白吐回去」本來就不可能讓比對成功，佔有式只是省掉這些注定失敗的嘗試。

### 5.2 地址規則：只從一段空白的開頭起算

佔有式解決了「切法」的爆炸，但每個起點仍要往後掃完整段空白，還是 O(n²)。
因此在規則最前面加上 `(?:(?<!\s)|(?=\S))`：一個起點若前一個字是空白、自己也是空白
（也就是在一段空白的**中間**），立刻放棄，O(1)。

**為什麼結果相同**：舊規則用「最左比對」。如果從空白中間某處能比對成功，
從這段空白的**開頭**也一定能成功：開頭的 `\s*` 可以多吃掉前面那些空白，之後完全一樣。
所以舊規則回傳的比對本來就一定從空白開頭開始。新規則只是不再嘗試那些不可能被選中的起點。

這裡有一個陷阱：比對結果會**包含前面的空白**。如果圖省事改成「比對不能從空白開始」，
結果會變（被遮掉的範圍與佔位符 ID 都不同）。所以新增了一個測試把這個行為釘住：
`"在  中山路12號3樓"` 的地址比對要從第一個空白開始。

### 5.3 email：本地部分上限 64 字元

改成 `[a-zA-Z0-9._%+-]{1,64}@…`。64 是 RFC 5321 對本地部分的上限，每個起點最多往後掃 64 個字元，所以是線性。

**沒有用的做法**：同樣的「只從一串字元的開頭起算」（lookbehind）也能變成線性，但會漏遮。
例如 `a@b.com1x@y.com`：第一個比對結束在 `com` 後面，下一個 email `1x@y.com` 的開頭緊接在一個字母之後，
lookbehind 會拒絕它，第二個 email 就漏掉了。保留這個例子當測試。

**行為差異**：只有本地部分超過 64 字元時才不同（不合規格的地址）；這時仍會遮住最後 64 個字元和網域。

### 5.4 實體重疊檢查：排序後二分搜尋

已選的實體與佔位符都是**互不重疊**的區間。照起點排序後，和 `(s, e)` 重疊的只可能是
「最後一個起點小於 e 的區間」，用 `bisect` 一次就找到：每個候選 O(log n)。選出的集合與舊版相同。

### 5.5 字串重組：一次組好

依序收集「兩個實體之間的原文」與佔位符，最後 `"".join(...)` 一次。
`triggered`（觸發的規則清單）保持舊版的順序。

### 5.6 大小上限：量遮罩實際處理的長度

- 新增 `masking.detection_length(text)`：原始長度與正規化後長度取大，絕不低估。
- gateway 的 `_scan_tokens`：原始長度已經超過上限時直接回傳，**不做正規化**，
  所以超大輸入在 413 之前不做任何事（分析的處理函式是非同步的，正規化 5 MB 會卡住事件迴圈）。
- 遮罩預覽與分析的 token 估計都改用這個值。

## 6. 驗證

### 6.1 逐條規則計時（上限附近，最壞輸入）

| 輸入 | 修正前 | 修正後 |
|---|---|---|
| 一長串空白 | 3,000 個就 49.5 秒；96K 跑不完 | 96K：0.036 秒 |
| 96K 個 `a`（email 本地部分）| 9.7 秒 | 0.11 秒 |
| `Applicant: Ab, Ab, …` 96K | 33.5 秒（審查量測）| 0.34 秒 |
| `申請人：㍻、㍻、…`（NFKC 2 倍）| 48K 就 33.7 秒（審查量測）| 96K：0.31 秒 |
| `ﷺ` × 96K（NFKC 18 倍）| — | 3.6 秒；現在在上限就被擋下（413） |

（修正前後都是同一台筆電、`NER_BACKEND=rules`。量測程式第一版沒有中途輸出，放到背景跑了 10 分鐘都看不出卡在哪，
後來改成每一項即時輸出、先用小的 N 找出最慢的組合，見 P-20。）

### 6.2 新舊版本的差異測試

把修正前的模組另存一份，用同一批隨機文字分別執行，比較三件事：地址比對、實體區間、最後的遮罩輸出。

- 第一版的隨機文字幾乎沒有地址：3 萬筆裡只有 6 筆有地址比對、0 筆從空白開始。
  「0 個差異」因此**沒有意義**。是加了計數才發現。
- 改用結構化的地址產生器：縣市、區、路名、段、巷、弄、號、樓、之，各自隨機出現，
  中間隨機插入各種空白（半形、全形、Tab、換行），前面再接隨機的前綴。
- 結果：3 萬筆中 **9,585 筆有地址比對、5,350 筆的地址從空白開始**（改動最敏感的情況）、
  14,846 筆有實體，**0 個差異**。

### 6.3 突變檢查（把舊行為放回去，測試必須失敗）

| 放回的舊行為 | 失敗的測試 |
|---|---|
| 舊的地址規則 | 3,000 個空白的計時測試（跑了 50.7 秒才失敗） |
| O(n²) 的重疊檢查 | 英文人名的計時測試 |
| 沒有上限的 email | 一長串本地部分字元的計時測試 |
| 上限只看原始長度 | NFKC 擴張的輸入應回 413 |
| 先遮罩再檢查上限 | 「回 413 時完全不執行遮罩」 |

### 6.4 既有測試

遮罩、egress、Unicode、實體的單元測試加上相關整合測試共 176 個；提到分析、配額、硬上限的 58 個測試檔共 550 個；全部通過。

## 7. 已知限制與後續

- **租戶字典的正規表示式沒有檢查。** 每個租戶可以上傳自己的規則（`data/tenant_dicts/`），
  寫得不好的規則同樣可能災難性回溯。目前只有營運者能上傳，列為後續：上傳時用刁鑽輸入計時、超過門檻就拒絕。
- **單一行程。** 線性之後，單一請求的成本有上限，但仍在 gateway 行程裡執行。
  更徹底的做法是把遮罩放到有逾時的工作行程（例如 process pool），逾時就中止。
- 本案修正正在進行獨立審查（重點：有沒有任何輸入遮得比以前少）；結論出來後補在這裡。

## 8. 學到的事

1. **大小上限不等於成本上限。** 只要演算法是超線性，上限以內的最壞輸入仍可能慢到不能用。
   修效能問題要在上限的最壞輸入上**重新量**，不能只加上限。
2. **逐個元件量，不要只量總時間。** 總時間只告訴你「慢」；逐條規則計時才找到真正的元兇，
   而且比審查回報的更嚴重。
3. **改安全關鍵的程式，用差異測試證明結果不變。** 而且要統計測試實際觸發了多少比對，
   否則「0 個差異」可能只是什麼都沒測到。
4. **看起來等價的寫法不一定等價。** lookbehind 版的 email 規則也是線性，但會漏遮；
   「不能從空白開始」的地址規則也是線性，但會改變遮罩範圍。兩者都用具體反例排除，並留成測試。
5. **突變檢查證明測試有用。** 每一個修正都把舊行為放回去，確認對應的測試會失敗。
