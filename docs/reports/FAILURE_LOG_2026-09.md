## B-1　Sentry 可能把未遮罩的 OA 原文送出本機（2026-09-29，已修正）

- **原因**：誤以為 `send_default_pii=False` 就不會送出內容。實際上它只管 cookie、header、IP；Python SDK 預設 `include_local_variables=True`、`max_request_body_size="medium"`，並會附上 logging breadcrumb。程式註解還寫「OA 內容已經遮罩過」，但在 `masking.redact()` 之前丟出的例外不成立。前端 SDK 也會附上例外訊息、console／fetch breadcrumb。
- **影響**：只要設定了 `SENTRY_DSN`（尤其是 sentry.io），例外發生時未遮罩的 OA 就會繞過遮罩、egress guard、機密路由（不變量 #3、#7）直接出境。預設沒有設定 DSN，所以尚未實際發生。
- **怎麼發現**：以「隱私、延遲最不能接受」為標準重新檢視系統時，讀 `observability.py:268`，再對照 Sentry 官方文件確認預設值。
- **修正**：後端關閉區域變數和請求 body，加上 `scrub_sentry_event()`；前端加上 `sentryScrub.js`。測試：後端 4 個、前端 3 個，全部通過。詳見 `docs/SECURITY_AUDIT.md` H-9。
- **教訓**：「關掉 PII」這類選項的範圍要查文件確認，不能看名字猜。第三方 SDK 是繞過自家防線最常見的路徑，現有測試抓不到，因為測試環境本來就沒有 DSN。

## B-2　稽核鏈在多個行程同時寫入時會分岔（2026-09-29 發現，2026-09-30 已修正）

- **原因**：「讀鏈尾 → 算 hash → 插入」只用 `threading.RLock` 保護，這把鎖只在單一行程內有效；讀鏈尾和插入也不在同一個資料庫交易裡。
- **影響**：部署多個 gateway 副本、共用同一個資料庫時，兩筆紀錄會接在同一個鏈尾之後，驗證時會被誤判成竄改。單機 demo 和既有的所有測試都在單一行程內，所以一直沒被發現。
- **怎麼發現**：以「從單機走向多副本」的角度審查設計時讀到 `audit.py:433`。**修正前實測重現**：4 個行程各寫 40 筆，160 筆紀錄只有 157 個不同的 `prev_row_hash`，分岔 3 次。
- **修正**：各 backend 實作 `_append_chained()`，讀鏈尾和插入放在同一個交易裡，並加上跨行程的鎖（SQLite `BEGIN IMMEDIATE`、Postgres `pg_advisory_xact_lock`）。新測試在舊程式上會失敗、在新程式上會通過。
- **Postgres 路徑**：2026-09-30 CI 的 `backend-services` 在真的 Postgres 16 上跑過 `test_audit_postgres.py`，全部通過（單一寫入者）。**多行程同時寫入 Postgres 的測試仍待補。**
- **教訓**：「測試全綠」只代表在測試的假設下正確。單一行程的測試證明不了多副本的正確性，要有真的開多個行程的測試。

## B-3　撤銷清單的 Redis 故障沒有處理（2026-09-29 發現，2026-09-30 已修正）

- **原因**：`RedisRevocationStore` 直接讓 Redis 的例外往上拋。
- **影響**：Redis 故障時回 500 而不是清楚的 503；登出也會出錯，使用者可能誤以為已經登出。
- **修正**：改成 `RevocationUnavailable`，回 503 加上 Retry-After，保持 fail-closed；登出失敗也會寫入稽核，不會回報成功。
- **附帶確認**：原本懷疑的「認證失敗不寫稽核」是真的，而且範圍比 Redis 故障更廣，**所有認證失敗都不會留下稽核紀錄**。已列為 `SECURITY_AUDIT.md` M-16，尚未修正。

## B-4　成本斷路器是全域的（2026-09-29 發現，2026-09-30 已修正）

- **原因**：`cost_circuit_state()` 只看全體的花費。雖然有記錄每個租戶的花費，但斷路器沒有使用。
- **影響**：一家事務所用量暴增，所有租戶都會被降級成便宜模型。
- **修正**：analyze 改用每租戶的斷路器（`COST_CIRCUIT_TENANT_DAILY_USD`）；全域門檻改為叢集的最後保險，預設從 100 提高到 1000。

## B-5　參考窗格看不到草稿引用的前案（2026-09-30 發現並修正）

- **原因**：`ReferencesPane` 用審查官引證的專利號（`cited_prior_art`）篩選檢索結果，但草稿的 `[GROUNDED_REF_n]` 是依核駁理由編號（`metadata.rejection_id` / `ref_index`，見 `lib/citations.js`）。兩者不一定重疊。
- **影響**：律師點草稿中的引用，右側參考窗格找不到對應的段落，無法核對來源；6 月實機截圖 `real_05` 就是「草稿有引用、右側顯示沒有命中」。對以「引用可核對」為核心的產品，這是信任訊號的破口。
- **怎麼發現**：前端改版時讀 `ReferencesPane.jsx` 與 `citations.js`，發現兩者的鍵不同。
- **修正**：新增 `hitsForRejection()`，依 `metadata.rejection_id` 取出該核駁的檢索結果（依 ref_index 排序），並標出哪些同時是審查官引證；舊版未標記的資料退回原本的篩選。測試 +2。
- **教訓**：同一份資料在兩個元件用不同的鍵對應時，要有一個共用函式當單一來源。

## B-6　工作台的預設案件沒有同步到上方的案件切換器（2026-10-01 發現並修正）

- **原因**：`Analyze` 在沒有「目前案件」時，自己用預設值 `CASE-2025-001`，但從來沒有寫回共用的 `CurrentCase`。
- **影響**：同一個畫面上三個地方說法不一：上方切換器顯示「尚未選擇案件」，工作台和信任帶卻用 CASE-2025-001（一般案件）。律師可能以為還沒選案件，或看錯路由等級。
- **怎麼發現**：第一次看改版後的畫面（CI 產生的截圖）。單元測試和 e2e 都只檢查各元件自己的狀態，沒有檢查彼此是否一致。
- **修正**：工作台掛載時若沒有目前案件，就把預設值寫回 `CurrentCase`。
- **教訓**：同一個事實在畫面上出現好幾次時，要有一個唯一來源；截圖檢查能抓到這種「各自都對、合起來不對」的問題。

## B-7　案件登錄頁收到格式不對的回應時，整個 SPA 當掉（2026-10-01 發現並修正）

- **原因**：`CaseAdmin` 直接讀 `data.levels.length`；回應缺 `levels` 時在 render 中丟出例外，被最外層的 error boundary 接住，整個 app 換成錯誤頁（導覽列也消失）。
- **影響**：舊版閘道、代理伺服器的錯誤頁、或錯的 mock 都會讓 IT 管理員的登入落點整頁當掉。
- **怎麼發現**：CI 的手機版 e2e（見 P-5）。
- **修正**：新增 `normalizeRegistry()`，任何格式不對的回應都變成空的登錄表；測試 +3。頁面同時改用新的設計元件（階段 4）。
- **教訓**：外部資料進 render 之前要先正規化；只有一個最外層 error boundary 時，任何一頁的小錯都會變成整個 app 的錯。

## B-8　CI 的 e2e 失敗截圖被後面的步驟清掉（2026-10-01 發現並修正）

- **原因**：桌面、手機、視覺三個 Playwright 步驟共用 `test-results/`，Playwright 每次執行前會清空輸出資料夾，最後跑的視覺步驟把前面的失敗截圖和 trace 全部刪掉。
- **影響**：連續兩次手機版失敗都拿不到截圖，只能從文字 log 和程式碼推斷原因，多花了診斷時間。
- **修正**：三個步驟各自用 `--output=test-results/{desktop,mobile,visual}`；上傳的 artifact 仍是整個 `test-results/`。
- **教訓**：CI 的 artifact 要在「失敗時」實際打開看一次，確認真的有東西。

## B-22　第一波引入的回歸：過長的請求 ID 讓分析在跑完模型後才失敗（2026-10-03 發現並修正）

- **原因**：B-14 讓回應改用閘道綁定的 `X-Request-ID`。清理函式允許最長 **200** 字元（`observability.py`），但 `AnalysisResponse.request_id` 的上限是 **128**（`models.py:482`）。修 B-14 時只看了「ID 從哪裡來」，沒有檢查「ID 要放進的欄位有什麼限制」。
- **影響**：
  - 用戶端送一個 129–200 字元的 `X-Request-ID`，解析、草擬、驗證都會照常跑完，到了最後組裝回應才驗證失敗，回 500。
  - 失敗路徑會把預留的用量整筆退回，所以模型費用不計入配額，也不觸發成本斷路器。等於可以重複白用模型，直到撞上每分鐘請求上限。
  - nginx 會覆寫這個 header，但 Vite 開發代理和直連 :8010 不會；digiRunner 是否覆寫尚未確認。
- **怎麼發現**：後端對抗式審查（V-B1）。
- **修正**：
  - 清理函式上限改成 128，和回應欄位一致。
  - 協調器另外檢查一次，超過就改用新產生的 uuid（`_user_facing_request_id`），避免兩個上限日後又分開。
  - 整合測試：用 300 字元的 ID 送出分析，必須回 200 且 ID ≤ 128。
- **教訓**：把一個值接到新的地方時，兩端的限制都要對一次（長度、字元、格式）。「晚失敗」特別危險：成本已經發生，失敗路徑卻把帳退掉了。（「失敗時退回預留用量，但成本已經花掉」這個更大的設計問題，列入第二波。）

## B-23　LLM 錯誤指標在 anthropic 模式下仍然永遠是 0（2026-10-03 發現並修正）

- **原因**：B-18 只把「降級標籤（`-DEGRADED-`）」算成 LLM 錯誤。anthropic 模式出錯時是直接拋出例外，推論端點回 500，`record_llm_usage` 根本不會被呼叫。程式碼裡唯一讀 `llm_error` 的地方，也從來沒有人寫入。
- **影響**：雲端模型整段停擺、拒答、或被擋下的 injection，`llm_errors_total` 都維持 0。這正是 B-18 想修的「結構上永遠綠燈」。
- **怎麼發現**：後端對抗式審查（V-B2）。
- **為什麼測試沒抓到**：B-18 的契約測試只用正規表示式找「程式碼裡有沒有 `LLM_ERRORS.inc(`」這段字。字串存在，但那一行在 anthropic 模式下永遠不會執行。見 P-8。
- **修正**：
  - AI 引擎的中介層：推論端點（parse、draft、verify、element comparison）回 5xx 就計一次 LLM 錯誤，標籤是 `<LLM_MODE>:request-failed`。
  - 新增行為測試：讓 parse 拋例外，檢查計數確實 +1。

## B-24　「降級結果不快取」漏掉多條備援路徑（2026-10-03 發現並修正）

- **原因**：B-15 只認兩種降級：模型標籤含 `-DEGRADED-`，以及佔位草稿。下列備援路徑都不會留下這兩種痕跡：
  - 檢索失敗後用空的引用集合繼續。
  - 請求項樹失敗。
  - 要件對照失敗。
  - 模型輸出不是 JSON：解析悄悄變成「零條核駁」，草擬變成空字串。
- **影響**：例如 Qdrant 抖動 10 秒，草稿就會沒有任何引用；律師按重試，接下來一小時拿到的都是快取裡這份沒有引用的結果。
- **怎麼發現**：後端對抗式審查（V-B3）。
- **修正**：
  - 協調器在每個備援點記下 `fallback_steps`，任一項就算降級、不寫快取。
  - AI 引擎在模型輸出無法解析時回傳 `output_unparseable`。
  - 整合測試：檢索失敗那次不快取，下一次也不會是快取命中；作為對照，正常結果會被快取。

## B-25　刪除個資時讓快取失效的機制會「失敗開放」，報告還宣稱已處理（2026-10-03 發現並修正）

- **原因**：
  - Redis 讀取失敗時 `get` 回傳 None，世代就被當成 0。
  - 遞增是「先讀再寫」，不是原子操作。
  - 寫入失敗只記 log。
  - `erase_subject` 不論成敗，都把 Redis 快取報告為「已涵蓋」。
- **影響**：
  - Redis 不通時，對照表照樣刪掉，報告寫已涵蓋，但快取裡的結果在 TTL 內仍讀得到。
  - 遞增途中讀取失敗會寫入世代 1，可能把已經作廢的舊項目重新變成可讀。
  - Redis 的 `allkeys-lru` 淘汰也可能把世代鍵清掉。
  - 報告也沒提到：密文仍留在 Redis 與它的 AOF／RDB 檔裡，沒有做到 ADR-01 的密碼學銷毀。
- **怎麼發現**：後端對抗式審查（V-B5）。
- **修正**：
  - Redis 後端新增 `get_or_raise`，能區分「沒有這個鍵」和「讀取失敗」。
  - 讀不到世代時整個請求不讀也不寫快取（fail closed，依 ADR-02 對隱私控制的原則）。
  - 遞增改用 `INCR`；失敗時拋出 `CacheUnavailable`，刪除報告會寫明「遞增失敗」。
  - 遞增成功時也照實寫：舊項目只是讀不到，密文要到 TTL 才消失。
  - 每個請求只讀一次世代（V-B10）。
  - 測試：Redis 斷線時不會讀到世代 0、遞增失敗會拋出、刪除報告會列出失敗、快取金鑰與對照表金鑰互不能解密。
- **仍未處理**：世代鍵被 LRU 淘汰的風險（機率低），已在程式註解說明。

## B-26　切換案件的競態只修了一半（2026-10-03 發現並修正）

- **原因**：B-12 用 `caseRef` 記住目前的案號，但它在 passive effect 裡、而且依 `caseId` 更新，要等「切換後的下一次渲染」才生效。如果分析回應剛好在這段空檔回來，A 案的結果仍會顯示在 B 案下。
- **另外三個缺口**：切換時沒有清掉舊案的錯誤（它的「重試」會對新案執行）；遮罩預覽沒有同樣的檢查；而 FAILURE_LOG B-12 寫著「待補競態測試」，卻沒有人補。
- **怎麼發現**：前端對抗式審查（V-F1、V-F4）。
- **修正**：
  - 改用 `useLayoutEffect`，並以外框傳入的案號為準，和切換在同一次 commit 內更新。
  - 切換時清掉錯誤；遮罩預覽也做相同的案號檢查。
  - 新增 e2e：先卡住分析回應，從上方切換案件，再放行，確認結果不會顯示，並跳出提示。
- **教訓**：「待補測試」寫在紀錄裡等於沒補；競態的修正一定要有能重現競態的測試。

## B-30　協調器改寫後，每次失敗的分析都會在日誌留下「exception was never retrieved」（2026-10-04，送出前發現並修正）

- **原因**：改成相依排程時，我用 `asyncio.gather` 包住各核駁的任務，再用 `asyncio.wait` 同時等它和「期限」任務。期限失敗時取消 gather；被取消的 gather 會把 `CancelledError` 設成自己的例外，而沒有任何程式去取它。
- **影響（若送出）**：每次期限失敗或時間用完的分析，日誌都多一筆 asyncio ERROR 和整段 traceback。錯誤告警與 Sentry 會充滿雜訊，真正的錯誤更難找。

- **修正**：不用 gather，直接等各個任務並逐一取結果；取消後的排水也把已結束任務的例外標為已讀。
- **測試**：`test_a_failed_deadline_stops_the_drafts_instead_of_waiting` 用 caplog 加 `gc.collect()` 斷言沒有「never retrieved」。我把 gather 暫時放回去重跑，這個測試確實會失敗，之後才還原。
- **教訓**：測試全過時，輸出裡的 ERROR 日誌也要看。取消 gather 的程式要負責取走它的例外。

## P-9　Claude 在第二波 a 實作中的失誤（2026-10-04，都在送出前發現）

1. **single-flight 第一版有競態。** 「查有沒有進行中的同樣分析」和「登記自己」之間隔了一個 await（查斷路器），兩個同時到的請求都會成為領頭者。自我檢查時發現，改成兩者之間沒有 await。
2. **差點讓被取消的請求不寫稽核列。** 原本打算把 finally 裡的稽核寫入改成 `await run_in_threadpool(...)`。但 anyio 的取消是持續有效的，`run_in_threadpool` 送出前又會先檢查取消，所以被取消的請求會整列不寫，違反不變量 #4。改成在第一個 await 之前就把寫入送進執行緒，並加測試（連續取消兩次仍寫入）。
3. **測試輔助函式會卡死。** `_run_two` 第一版在 `with ThreadPoolExecutor` 裡等待；斷言一失敗，離開 with 就會等一個永遠不會放行的請求。執行前發現，改成失敗時先放行。
4. **又對 pytest 加了 `--timeout`，卻沒裝 pytest-timeout。** P-3 記過同一件事。
5. **突變檢查第一次沒有生效**：檔案是 CRLF，PowerShell 用 `` `n `` 取代找不到字串。改用 `` `r`n `` 後才真的跑到。
6. **啟動警告過時。** 它仍以「每次呼叫的等待」判斷會不會超過前端的 420 s，但截止時間上線後，該看的是 `ANALYZE_DEADLINE_SEC`。已改。

- **教訓**：
  - 「檢查後登記」之間不能有 await。
  - 在可能被取消的工作裡，finally 中的 await 不一定會執行；必須執行的副作用要在第一個 await 前送出。
  - 會卡住的測試，要在失敗路徑上先放行。
  - 重複的失誤（第 4 點）已寫進記憶，下次執行前先查。

## P-8　Claude 在第一波高估了自己的修正與測試（2026-10-03）
